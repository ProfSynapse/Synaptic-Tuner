# Implementation Plan: Unified Training and Job APIs

> Generated by `pact-codex-plan-mode` on 2026-08-25  
> Status: APPROVED — IMPLEMENTATION MAY PROCEED UNDER PACT GATES

## Summary

Replace the historical local/cloud/backend split with a clean submodule-owned
architecture. `TrainingAPI` owns typed model-training intent and compiles it
into an immutable workload; `JobAPI` owns durable execution, provider
lifecycle, logs, cancellation, authorization, and artifacts. The CLI becomes a
thin adapter with `train` for training and `job` for lifecycle operations.

This is a breaking cutover. The rejected seven-file compatibility prototype is
discarded, and `cloud`, `cloud-run`, `local-run`, and `cloud-jobs` are
deleted rather than aliased or deprecated.

## Product Contract

### Primary user experience

```text
tuner train
tuner train --config training.yaml --plan
tuner train --config training.yaml --yes
tuner train --config training.yaml --yes --detach

tuner job list
tuner job show RUN_ID
tuner job logs RUN_ID --follow
tuner job cancel RUN_ID
```

- Interactive and config-driven training construct the same typed
  `TrainingRequest`.
- `--plan` is explicitly non-executing.
- `--json` changes representation only; it never changes execution semantics.
- Attached observation is the default. `--detach` returns after durable
  provider acceptance.
- Ctrl+C stops local observation but does not cancel remote work.
- Old commands fail parsing; there are no compatibility routes.

### Advanced arbitrary jobs

`JobAPI` supports lifecycle operations for every training-created job.
Arbitrary submission is a separately entitled advanced/admin capability:

```text
tuner job run --config job.yaml --plan
tuner job run --config job.yaml --yes --detach
```

Do not expose `job run` in the beginner menu or primary training docs. Do not
ship arbitrary submission until at least two providers satisfy the full job
conformance contract. Training recipes can never contain shell commands or
`run.steps`.

#### Domain boundaries

| Component | Responsibility | Must not own |
|---|---|---|
| `TrainingAPI` | Training recipe parsing, method validation, canonical defaults, model/dataset resolution, workload compilation, training outcome | Provider SDK calls, job polling, cancellation, credentials |
| Method compiler | SFT/KTO/GRPO/embedding semantics and deterministic workload | Provider selection, credentials, mutable defaults |
| `JobAPI` | Source policy, grants, durable submit/reconcile, lifecycle, logs, cancel, artifact references | Training semantics or recipe heuristics |
| Execution provider | Provider-specific prepare/submit/status/logs/cancel | YAML parsing or training hyperparameter mapping |
| Artifact store | Durable slot allocation, manifests, inventory, verification | Training-method selection |
| CLI | Input collection, plan display, confirmation, output formatting | Handler-to-handler routing or provider construction |
| Experiment orchestration | Compose training/evaluation/loss/analysis APIs | Direct backend/handler construction |

#### Public contracts

Create or replace public types under `synaptic_tuner.api.v1`:

- `TrainingRequest`, `ModelSpec`, `DatasetSpec`,
  `TrainingParameters`, `AdapterSpec`, `ExecutionSpec`,
  `ArtifactPolicy`
- `TrainingPlan`, `TrainingSubmission`, `TrainingOutcome`,
  `TrainingAPI`
- `JobRequest`, `JobPlan`, `JobSubmission`, `JobAPI`
- `RunRef`, `RunState`, `RunStatus`, `LogCursor`, `LogEntry`,
  `LogPage`, `CancelResult`, `ProviderDescriptor`
- `ExecutionGrant`, `AuthorizationRequirement`, `ArtifactRef`

Plans are frozen, serializable, secret-free, and deterministically
fingerprinted. They never contain private backend/config objects or a mutable
`_submitted` flag.

#### Lifecycle semantics

```text
PLANNED -> AUTHORIZED -> SUBMITTING
                          |-> SUBMITTED -> QUEUED -> RUNNING
                          |                         |-> SUCCEEDED
                          |                         |-> FAILED
                          |                         |-> CANCELLED
                          |-> NOT_SUBMITTED
                          |-> SUBMISSION_AMBIGUOUS
```

- `JobAPI` owns compute lifecycle.
- Artifact verification is a separate dimension:
  `PENDING | VERIFIED | FAILED`.
- A provider job may be compute-`SUCCEEDED` while artifact verification is
  pending or failed.
- Attached `train` returns success only when required artifacts are
  `VERIFIED`.
- Cancellation is a durable desired-state request. Only authenticated provider
  confirmation yields `CANCELLED`; ambiguous cancellation remains explicit.

#### Provider and method separation

Delete `ITrainingBackend` and `TrainingBackendRegistry` after callers
migrate. Replace them with:

- `TrainingMethodRegistry`: method compilers and method schemas.
- `ExecutionProviderRegistry`: static, lazy provider descriptors and
  factories.

Capability listing is metadata-only: no SDK import, credential read, network
call, CLI probe, or authorization. Explicit readiness/quote operations perform
those effects separately.

#### Configuration ownership

Training and arbitrary jobs use disjoint, versioned schemas:

- `schema_version: synaptic.training/v1`, `kind: training`
- `schema_version: synaptic.job/v1`, `kind: job`

Training schema rules:

- One canonical field spelling; no historical aliases.
- No `target`, `local:`, `cloud:`, or runner deep merge.
- No duplicate `run.method`.
- No `run.steps`, shell, arbitrary setup steps, or literal secrets.
- Execution placement lives under `execution.provider`.
- Unknown fields fail closed at every level.
- Model, dataset, image, and dependencies resolve to immutable revisions in the
  plan.

Training recipes remain under `Trainers/recipes/`. Arbitrary job recipes move
to `Jobs/recipes/`.

#### Source, authorization, secrets, and artifacts

- Remote execution binds exact host and engine commits, recipe/workload
  digests, model/dataset revisions, runtime image/lock, resources, artifact
  slot, quote, and allowed secret references.
- Local execution records a content-addressed workspace snapshot and dirty
  status; it does not inherit the remote pushed-commit rule.
- Paid execution consumes a durable, exact `ExecutionGrant` before credentials
  or provider mutation.
- Secret values resolve just in time after `SUBMITTING`; plans contain opaque
  references only.
- Every run receives an internally generated exclusive artifact slot.
- Provider completion does not imply artifact authenticity; manifests and
  bounded inventory must verify.

#### Protected HF boundary

`hf-source`, `hf-smoke`, and `hf-training-smoke` remain unchanged,
isolated operator/certification commands. Generic `TrainingAPI` or `JobAPI`
must not construct their protected workloads or weaken their option allowlists,
exact workload bindings, credential-free remote runtime, one-submit/one-cancel
claims, closed diagnostics, or exact artifact inventory.

## Synthesized Implementation Roadmap

### Agreements

All consultants agree:

- The current prototype must be replaced, not refined.
- `TrainingAPI` and `JobAPI` are separate submodule-owned domains.
- Training methods and execution providers are separate registries.
- Recipes are strict, versioned, and disjoint.
- Execution lifecycle and one-submit state are durable.
- The CLI contains no legacy aliases.
- Provider-specific safety remains below the CLI.
- Protected HF certification lanes remain isolated.

  separate state dimensions; user-facing attached training succeeds only after
  verification.
- **Arbitrary jobs (major product scope):** recommend lifecycle operations
  publicly, with arbitrary submission advanced/admin-only and gated until two
  providers conform.

## Approved Product Decisions

1. **Native local execution:** preserve CUDA and MLX through a trusted,
   compiler-only `process` provider. Do not preserve legacy handlers or accept
   caller-supplied commands.
2. **Job surface:** expose lifecycle operations over owned runs publicly.
   Withhold arbitrary submission from public `JobAPI`; any future submission
   API is separately entitled, disabled by default, and independently gated.
3. **Logs:** require authenticated, structured, bounded, redacted logs without
   training samples by default. Raw provider logs remain operator-only.

## Review Remediation Contract

This section is normative and supersedes any conflicting exploratory wording
elsewhere in this plan. Implementation remains blocked until SECURITY and TEST
re-review confirm that these controls and gates are enforceable.

### 1. Authorization and execution grants

- `--yes` acknowledges an already disclosed plan; it never creates, widens, or
  substitutes for execution authority.
- The authoritative `ExecutionGrant` is opaque, durable, and bound to actor,
  project, provider account and namespace, operation, canonical plan and exact
  source digests, resource limits, timeout, maximum cost, quote identity and
  expiry, exclusive artifact slot, publication policy, allowed secret
  references, grant expiry, and exactly one submission effect.
- The grant and durable uniqueness claim are atomically consumed when the run
  enters `SUBMITTING`, before secret resolution or provider mutation. Expired,
  mismatched, consumed, corrupt, or partially persisted grants fail closed.

### 2. Public lifecycle and administrative submission boundary

- Public `JobAPI` is lifecycle-only: `list`, `show`, `logs`, and `cancel` operate
  only on an authenticated actor's/project's owned `RunRef` values.
- Arbitrary submission is absent from or disabled by default in the public
  product. A future administrative API requires separate entitlement, policy,
  audit surface, documentation, and an independent security release gate;
  provider conformance alone cannot enable it.
- The administrative API accepts typed argv only, never shell text. It requires
  approved digest-pinned images, bounded CPU/GPU/memory/disk/process/time,
  narrow mounts/networking, and denial of privileged mode, host namespaces or
  devices, Docker socket, arbitrary capabilities, and undeclared secrets.

### 3. Durable submit, cancel, and reconcile semantics

- Submission states are `PLANNED -> AUTHORIZED -> SUBMITTING -> SUBMITTED`, with
  `NOT_SUBMITTED` and `SUBMISSION_AMBIGUOUS` effect-resolution branches.
  Cancellation uses `CANCEL_REQUESTED -> CANCELLING -> CANCELLED`, with
  `CANCEL_FAILED` and `CANCEL_AMBIGUOUS`. Reconciliation uses
  `RECONCILE_REQUIRED -> RECONCILING` and persists an authenticated provider
  observation before resolving ambiguity.
- Durable uniqueness covers actor/project, operation, canonical plan digest,
  grant, run, and provider-effect identity. Concurrent callers produce at most
  one provider effect and one cancellation effect.
- Required crash/corruption/concurrency cases are: before claim; after claim but
  before provider call; during call; after provider effect but before receipt;
  duplicate caller; conflicting cancel; corrupt/missing receipt; and reconcile
  races.
- No retry follows an ambiguous provider effect. Only read-only reconciliation
  may establish whether the original effect occurred; unresolved ambiguity
  remains explicit and operator-visible.

### 4. Immutable revision-resolution preflight

- Revision resolution is a distinct, disclosed, read-only preflight using
  narrowly scoped credentials and auditable network access. Unresolved inputs
  may be reported but cannot be authorized or submitted.
- Source, model, dataset, tokenizer, dependency lock, and runtime image resolve
  to immutable identifiers before canonical plan finalization and grant issue;
  both plan and grant bind those exact values.
- Provider adapters receive immutable bindings only. They may verify equality
  but cannot resolve mutable names, follow moving tags or branches, or rewrite
  bindings during prepare, submit, reconcile, or artifact handling.

### 5. Log access and minimization

- Every log operation authenticates the caller and authorizes `RunRef`
  ownership; provider job identifiers are never ownership proof.
- Public logs are structured, schema-versioned, cursor-paginated, size/rate and
  retention bounded, and redacted before persistence and display. Secrets,
  environment dumps, provider responses, credentials, raw prompts, training
  samples, and unrestricted tracebacks are prohibited.
- ANSI escape sequences, terminal controls, Unicode control and bidirectional
  controls, carriage-return overwrite sequences, and equivalent control
  characters are sanitized before persistence and sanitized again before
  display. Oversized records or streams fail boundedly without persisting or
  rendering attacker-controlled overflow.
- Raw provider logs are operator-only, separately entitled and audited, with
  stricter retention and the same secret-redaction floor.

### 6. Artifact containment and publication

- Artifact destinations are server-generated exclusive slots bound into plan
  and grant. Canonical paths must remain under the authorized root; absolute
  paths, traversal, alternate streams, normalization/case collisions,
  pre-existing targets, and cross-run collisions fail closed.
- Collection/publication reject symlinks, hard links, junctions, reparse points,
  devices, sockets, and identities escaping the slot. Identity is revalidated
  at open/read and publish boundaries to prevent link-swap races.
- A bounded inventory and content-digested manifest are atomically created in a
  new destination and verified before artifact state becomes `VERIFIED`.
  The manifest binds the canonical plan digest, exact source digest, provider
  account, provider namespace, provider job identity, and exclusive artifact
  slot identity. Partial, duplicate, unexpected, oversized, post-manifest
  mutation, or cross-run manifest/artifact substitution fails.
- Publication is a separate authorized operation bound to target namespace and
  policy. Compute success grants no publication authority; failed or unverified
  artifacts cannot be published.

### 7. Enforceable local execution profiles

- Docker enforces a versioned safe profile: approved digest-pinned image,
  non-root user, read-only root where supported, `no-new-privileges` or an
  enforceable platform equivalent, and no privilege, host/PID/network
  namespace, Docker socket, or added capabilities. Source, config, model,
  dataset, and dependency inputs are read-only; exactly one narrow artifact
  slot is writable. Resources, processes, and time are bounded; mounts are
  narrow and declared; network and secrets use explicit allowlists. Missing
  enforcement or limits makes the provider unavailable.
- CUDA/MLX `process` executes typed argv emitted only by a trusted registered
  method compiler for approved trainer entrypoints and immutable inputs. It has
  no arbitrary-command or shell escape hatch and is not the admin job API.

### 8. Trust boundaries, secrets, and provider registration

- Formal trust boundaries separate caller/CLI, parser/compiler,
  authorization/grant service, durable store, provider adapter, provider
  control plane/runtime, artifact store, log store, and operator diagnostics.
  Cross-boundary data is typed, authenticated where applicable, and minimized.
- Plans contain `SecretRef` only. Per-method/provider allowlists govern refs;
  values resolve after the durable `SUBMITTING` claim into a minimal child
  environment and are never inherited wholesale, serialized, cached, logged,
  returned in errors, or placed in argv.
- The production provider registry is static and locked. Recipes, plugins,
  environment variables, and remote responses cannot register or replace
  provider factories.
- Generic HF Jobs and protected HF certification lanes have separate
  registrations, policies, schemas, grants, stores, and release gates. Generic
  APIs cannot construct, select, invoke, or weaken protected HF workloads.

### 9. Method and provider readiness

- Maintain an explicit readiness matrix for every method (`sft`, `kto`, `grpo`,
  `embedding`) against every provider (`process`, `docker`, `modal`, `hf_jobs`,
  and later `runpod`). Each cell records compiler, strict-recipe migration,
  runtime, artifact, lifecycle/log/cancel, conformance, and release status.
- Unsupported, incomplete, unknown, or stale cells are unavailable through
  defaults, overrides, menus, workflows, or direct API construction.
- Each strict `synaptic.training/v1` recipe and semantic suite migrates with its
  method compiler before any provider, workflow, or CLI exposes that method.
  Providers advertise only operationally conformant cells.

### 10. Conformance, hostile tests, and cutover gates

- Operational provider conformance, using deterministic fakes and available
  no-cost real runtimes, proves prepare, submit, status, structured logs,
  cancel, reconcile, authentication, persistence, artifact handling, and
  capability refusal; metadata declarations are insufficient.
- P0 hostile tests cover forged/cross-project `RunRef`, grant replay/mismatch,
  expired/stale or scope-mutated grants, wrong provider identity, concurrent
  submit/cancel, ambiguous effects, corrupt receipt/store recovery, secret/log
  exfiltration, ANSI/terminal/Unicode control-character injection, oversized
  log records and streams, argv/shell injection, arbitrary submission without
  entitlement, malicious images, unsafe Docker privilege/namespace/socket or
  writable-input modes, missing Docker resource/process/time limits,
  `trust_remote_code` or equivalent remote-code activation, traversal and
  link/reparse races, artifact collision/mutation or cross-run substitution,
  registry injection, mutable revision drift, and attempts to reach protected
  HF via generic APIs.
- P0 cutover tests prove old commands/handlers and compatibility aliases are
  absent; every retained method has a strict recipe/compiler; unsupported cells
  fail closed; and higher workflows use public APIs, not legacy backends.
- P0 crash tests exercise every state/effect boundary from section 3, including
  restart and reconciliation. SECURITY and TEST re-review, applicable P0 gates,
  and operational readiness cells must be green before release.
