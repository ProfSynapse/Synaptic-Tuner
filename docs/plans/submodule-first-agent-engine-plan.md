# Implementation Plan: Submodule-First, Agent-First Synaptic Tuner Engine

> Generated by Codex on 2026-08-16
> Status: APPROVED
> Approved by Joseph Rosenbaum on 2026-08-16

## Executive Recommendation

Make Synaptic Tuner **submodule-first, but not submodule-coupled**.

The host repository should pin an exact Synaptic Tuner commit as a Git submodule and own all research-specific configuration, data, plug-ins, governance, state, and artifacts. Synaptic Tuner should own generic execution mechanisms and behave as a location-independent engine. A run must not depend on the engine being the current working directory, on the submodule having a particular folder name, or on host data being copied into the engine checkout.

The architectural center is a strict, versioned project contract:

1. `tuner/project/**` resolves engine, host, config, writable, plug-in, and source-provenance context.
2. `synaptic_tuner/api/v1` is the deliberately narrow supported public Python facade.
3. `synaptic.yaml` declares the host project contract.
4. `project_v1` path rules make config interpretation independent of cwd.
5. `.synaptic/{artifacts,state,tracking,cache,tmp}` are host-owned writable roots; host source and engine source are read-only during execution.
6. `tuner/project/source_bundle.py` produces one schema-versioned source lock containing both the host and engine source identities.
7. `tuner/cloud/checkout.py` and `tuner/cloud/runtime_layout.py` reconstruct and verify those sources for every provider.
8. The canonical cloud path clones the exact host superproject and initializes the engine recursively at the recorded gitlink. A verified dual-clone layout is secondary, for cases where a provider or host layout cannot use a submodule checkout.
9. Agent capabilities become machine-discoverable, including input schemas, side effects, cost/GPU requirements, confirmation requirements, resumability, and structured results/events.

The first implementation slice should establish `ProjectContext`, the host manifest, path semantics, the source lock, and a synthetic downstream-superproject contract test. That foundation is required before broad handler, Docker, or cloud changes. HF Jobs is the first provider integration; Modal and RunPod follow only after the provider-neutral source/runtime contract is proven.

This is an architectural evolution, not a rewrite. Existing standalone commands, trainers, evaluator behavior, config-first discipline, provider-native artifact layouts, and historical lineage remain valid.

## Goals

- Let a host repository embed Synaptic Tuner at any submodule path and invoke it from any working directory.
- Preserve exact Git pinning as the reproducibility boundary between host and engine.
- Keep the engine checkout clean and effectively immutable during host-project execution.
- Give every subsystem explicit engine, host, config, artifact, state, tracking, cache, and temporary roots.
- Resolve all project config paths deterministically and independently of process cwd.
- Keep project-specific prompt rendering, grading, reward, gates, datasets, and governance outside the engine.
- Support trusted project-local plug-ins without manual `PYTHONPATH` manipulation.
- Provide a narrow, versioned public API without prematurely declaring current internal abstractions stable.
- Make capabilities and execution effects machine-readable for coding and research agents.
- Record both host and engine sources, exact configs, plug-ins, runtime assets, and provider facts for every run.
- Make local Docker and cloud execution reconstruct the same logical project layout.
- Preserve current standalone behavior for users who do not opt into `synaptic.yaml`.
- Provide a staged downstream migration for Epistemic-Humility-Research without rewriting its historical provenance.

## Non-Goals

- Do not embed Epistemic-Humility-specific concepts, schemas, paths, graders, or protocols in Synaptic Tuner.
- Do not convert the repository to a monorepo or vendor host projects into the engine.
- Do not make Git submodules follow `main` during normal execution; the host gitlink remains authoritative.
- Do not rewrite historical `.tracking`, run records, lineage JSON, experiment manifests, or paper provenance.
- Do not redesign SFT, KTO, DPO, GRPO, embedding, evaluation, SynthChat, or MechInterp algorithms as part of the root separation.
- Do not make the existing `tuner.core.interfaces` hierarchy a supported public API in v1.
- Do not claim that project plug-ins are sandboxed. A trusted plug-in executes with the same authority as the engine process.
- Do not publish a supposedly self-contained wheel until the runtime-asset boundary is explicit and tested.
- Do not migrate Epistemic-Humility-Research in the same PR as the engine work.
- Do not replace provider-native artifact storage with one forced local storage backend.

## Reference Consumer: Epistemic-Humility-Research

Epistemic-Humility-Research is the reference consumer, not a source of engine-specific assumptions.

Verified downstream patterns:

- `.gitmodules` pins Synaptic Tuner under `synaptic-tuner/`.
- Host `AGENTS.md` declares the engine a separate, generic ownership boundary.
- Project configs, protocols, paper claims, datasets, renders, graders, gates, and outputs remain in the host.
- Commands run as `python synaptic-tuner/tuner.py ...` from the host root because config paths are host-root relative.
- Parse/import workflows manually add `synaptic-tuner` and project plug-in folders to `PYTHONPATH`.
- The locked training runner stages host data into `synaptic-tuner/scratch/eh_staging` before invoking `local-run` from the engine cwd.
- Run records independently capture the research repository commit and `submodule_commit`.
- Cloud wrappers sometimes clone host and engine separately at exact commits because the current engine cloud path models one source.
- Several harnesses locate `REPO_ROOT / "synaptic-tuner"` and inject it into `sys.path`.

These workarounds demonstrate the intended architecture:

```text
Host owns research intent and evidence
            │
            ├── exact gitlink ──► Engine owns generic mechanism
            │
            ├── host configs/plugins/data
            └── host state/artifacts/provenance
```

The engine change is successful when the downstream repository can remove cwd switching, data staging into the submodule, most `PYTHONPATH` manipulation, and hand-built dual-source provenance without moving its research logic into Synaptic Tuner.

## Primary-Source Best Practices

1. A Git submodule is a repository embedded at a path in a superproject, and the superproject records the commit expected at that path. `git submodule update` checks out the commit recorded by the superproject; `--recursive` extends that behavior to nested submodules. This supports exact dependency pinning and is the basis for the canonical cloud checkout. See the [Git submodule command documentation](https://git-scm.com/docs/git-submodule) and [Git submodule guide](https://git-scm.com/docs/gitsubmodules).
2. Git submodule status distinguishes an uninitialized submodule, a checkout that differs from the recorded gitlink, and a conflicted submodule. The cloud preflight must make those states explicit rather than treating engine `HEAD` alone as sufficient. See [Git's submodule status semantics](https://git-scm.com/docs/git-submodule#Documentation/git-submodule.txt-status--cached--recursive--ltpathgt82308203).
3. GitHub's official checkout action supports recursive submodule checkout. CI should use `submodules: recursive` and should still verify the exact gitlink after checkout. See [actions/checkout](https://github.com/actions/checkout).
4. Python console commands and plug-in discovery have standardized entry-point semantics. The `synaptic` command should use a `console_scripts` entry point, while installed plug-ins should use the dedicated, versioned `synaptic_tuner.plugins.<kind>.<vN>` entry-point group namespace defined by this plan. See the [PyPA entry-points specification](https://packaging.python.org/en/latest/specifications/entry-points/).
5. A `src/` layout reduces accidental imports from the repository root, but adopting it now would combine packaging with a high-risk repository-wide import migration. The public facade can be added without a full layout conversion; a future packaging RFC may revisit it. See [PyPA's src-layout discussion](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/).
6. Semantic Versioning applies only after a public API is declared. This plan versions the manifest, source lock, capability schema, result/event envelopes, and `synaptic_tuner.api.v1`; it does not promise stability for all current internal modules. See [Semantic Versioning 2.0.0](https://semver.org/).
7. Host `AGENTS.md` files should remain authoritative for host-project agent instructions. The engine should expose machine-readable capabilities and generic operational context, not copy consumer instructions into the submodule. See the [AGENTS.md convention](https://agents.md/).

## Resolved Architectural Decisions

| Decision | Resolution | Rationale |
|---|---|---|
| Architectural posture | Submodule-first, not submodule-coupled | Exact pins without cwd/path coupling |
| Internal project subsystem | `tuner/project/**` | One owner for roots, paths, manifests, configuration, plug-ins, and sources |
| Public Python facade | `synaptic_tuner/api/v1` | Stable surface without freezing internals |
| Initial public release | Synaptic Tuner `1.1.0`; `synaptic_tuner._version.__version__` is canonical | Records the approved additive release and prevents package, public, legacy, and CLI version drift |
| Engine/environment precedence | Resolve engine root before dotenv; select one mode-appropriate dotenv; preserve existing process values | Prevents a dotenv file from redirecting engine code or overwriting operator/provider environment |
| Host manifest | `synaptic.yaml`, schema `synaptic-project/v1` | Visible, versioned project identity |
| Strict path mode | `project_v1` | Deterministic config-relative and URI semantics |
| Compatibility mode | Standalone legacy when no host contract is selected | Prevents an involuntary breaking release |
| ML host adapter seam | Resolve host ML data/output references in `MLHandler`, then call a reusable validated-config seam in `Trainers/ml/train.py`; retain standalone `main(config_path)` | Handler-only adaptation cannot work because the trainer reopens unresolved YAML; this boundary avoids cwd mutation, temporary rewritten configs, and duplicated trainer orchestration |
| Writable roots | `.synaptic/{artifacts,state,tracking,cache,tmp}` | Keeps source trees immutable and separates durability classes |
| Source roots | Host and engine source are read-only at runtime | Prevents dirty submodules and evidence/source mixing |
| Canonical cloud source | Recursive host-superproject checkout plus exact gitlink verification | Uses the host commit as the dependency lock |
| Secondary cloud source | Verified dual clone | Supports providers/layouts that cannot initialize the submodule directly |
| Source model | `tuner/project/source_bundle.py` plus one source-lock schema | Avoids competing `RepoSource`, bundle, and lineage models |
| Cloud reconstruction | `tuner/cloud/checkout.py` | Provider-neutral checkout/verification logic |
| Runtime filesystem mapping | `tuner/cloud/runtime_layout.py` | One mapping shared by local Docker and cloud providers |
| Provider order | HF Jobs, then Modal, then RunPod | Proves the current canonical cloud lane first |
| Plug-in trust | Full-authority trusted extensions | Honest threat model; no false sandbox claim |
| Plug-in compatibility | Logical bindings, authoritative versioned entry-point groups, and raw `module:callable` adapter | Improves discovery without breaking current configs while making installed kind/API metadata verifiable without import |
| Wheel release | Gated on a defined runtime-asset boundary | The engine depends on scripts/configs outside `tuner`; a premature wheel would be incomplete |
| Downstream adoption | Separate Epistemic-Humility PR | Keeps generic engine review separate from consumer migration |
| Historical records | No rewrites | Existing provenance remains evidence of the execution contract at that time |

## Contract 1: Project Context and Root Resolution

```python
@dataclass(frozen=True)
class ProjectContext:
    engine_root: Path
    project_root: Path
    config_root: Path
    artifact_root: Path
    state_root: Path
    tracking_root: Path
    cache_root: Path
    tmp_root: Path
    invocation_cwd: Path
    manifest_path: Path | None
    mode: Literal["standalone", "host"]
    path_mode: Literal["legacy", "project_v1"]
```

### Project-root precedence

1. `--project-root`
2. `SYNAPTIC_PROJECT_ROOT`
3. Nearest `synaptic.yaml` ancestor of the primary config document
4. Nearest `synaptic.yaml` ancestor of invocation cwd
5. Git superproject of `engine_root`
6. Standalone fallback: `project_root = engine_root`

If the config document and cwd discover different manifests, fail with `PROJECT_ROOT_AMBIGUOUS`; do not guess.

### Engine-root rules

- Engine-root precedence is: explicit Python `engine_root` argument, then the pre-existing process value of `SYNAPTIC_ENGINE_ROOT`, then the package/module-location fallback.
- The package/module-location fallback derives the engine root from package/module resources for source execution and uses package-resource metadata plus the configured runtime-asset boundary for installed execution.
- `SYNAPTIC_ENGINE_ROOT` is a process-level development/test override, not normal host or dotenv configuration.
- Engine-root resolution completes before any dotenv file is selected or loaded. A value read from `--env-file`, host `.env`, or standalone engine `.env` cannot retroactively change the resolved engine root.
- The host manifest cannot silently redirect the engine implementation root.

### Environment loading

- Dotenv **file selection** is: explicit `--env-file`; otherwise host `.env` in host mode; otherwise engine-root `.env` in standalone legacy mode. This ordering selects a file and is not value precedence.
- The selected dotenv is loaded with `override=False`; pre-existing process environment values win over values in that file.
- Host mode does not automatically load the engine checkout's `.env`.
- Secrets are never copied into source locks, resolved configs, events, or artifacts.

## Contract 2: Host Manifest

```yaml
schema_version: synaptic-project/v1

project:
  id: example-research
  name: Example Research

engine:
  requires: ">=1.0,<2.0"
  api: v1

paths:
  configs: project://experiments
  artifacts: project://.synaptic/artifacts
  state: project://.synaptic/state
  tracking: project://.synaptic/tracking
  cache: project://.synaptic/cache
  tmp: project://.synaptic/tmp

configuration:
  profiles:
    default:
      - engine://configs/defaults.yaml
      - project://configs/tuner-defaults.yaml

plugins:
  search_paths:
    - project://experiments/common
  bindings:
    example.prompt:
      kind: renderer
      api: synaptic.plugin/renderer/v1
      target: renders.example:render
    example.grade:
      kind: grader
      api: synaptic.plugin/grader/v1
      target: graders.example:grade

policies:
  engine_writes: deny
  source_writes: deny
  external_paths: warn_local_deny_cloud
  dirty_sources: deny_cloud
```

Validation rules:

- Unknown schema major is fatal.
- Unknown same-major optional fields warn and remain available to round-trip tooling.
- `engine.requires` is checked before handler execution.
- All declared roots pass symlink-aware containment checks.
- Writable roots cannot be nested below the engine root in host mode.
- Host source paths remain read-only even though they share the project filesystem with `.synaptic`.

## Contract 3: Layered Configuration

Precedence, lowest to highest:

1. engine built-in defaults;
2. engine named profile;
3. host manifest profile/defaults;
4. included config documents in declaration order;
5. primary config document;
6. explicit CLI overrides.

Environment variables are not a hidden general-purpose configuration layer. They remain reserved for root discovery, credentials, and already-documented provider facts.

Every planned or executed run emits a resolved-config record under the tracking root:

```json
{
  "schema_version": "synaptic-resolved-config/v1",
  "config": {},
  "sources": [
    {
      "uri": "project://experiments/example/job.yaml",
      "sha256": "...",
      "precedence": 50
    }
  ],
  "overrides": [
    {
      "path": "training.max_steps",
      "source": "cli",
      "value": 20
    }
  ],
  "resolved_sha256": "..."
}
```

The record contains resolved values and hashes, but not secrets.

## Contract 4: Paths and URI Semantics

| Scheme | Base | Access expectation |
|---|---|---|
| `project://` | `project_root` | Host source reads; paths under declared `.synaptic` roots may write |
| `engine://` | `engine_root` | Read-only in host mode |
| `config://` | Declaring document directory | Normally read; output fields must still target a writable root |
| `artifact://` | `artifact_root` | Durable writes |
| `state://` | `state_root` | Resume/operational writes |
| `tracking://` | `tracking_root` | Registry, lineage-index, config, and source-lock writes |
| `cache://` | `cache_root` | Regenerable read/write |
| `tmp://` | `tmp_root` | Recoverable temporary writes |
| `file://` | Explicit absolute local path | Opt-in external input; cloud requires declared transport |

In `project_v1`:

- Bare relative paths in YAML/JSON resolve from the declaring document directory.
- CLI filesystem arguments resolve from invocation cwd unless passed as a URI.
- Included documents keep their own declaring directories.
- `..` traversal cannot escape a scheme root.
- Containment checks occur after symlink resolution.
- Windows drive letters are not interpreted as URI schemes.
- Output fields cannot resolve into host source or engine source.
- Absolute/file paths may be used locally under policy, but cloud preflight fails unless they have a declared transport.

In standalone legacy mode, current subsystem-specific behavior remains intact. Strict reinterpretation occurs only after a project contract is selected.

## Contract 5: Public API and Plug-ins

### Supported facade

```python
from synaptic_tuner.api.v1 import (
    ProjectContext,
    PathRef,
    PluginContext,
    CapabilityDescriptor,
    EventEnvelope,
    ResultEnvelope,
    SourceLock,
)
```

The v1 facade re-exports stable contract types. It does not re-export all current `tuner`, `shared`, trainer, evaluator, or MechInterp internals. Synaptic Tuner `1.1.0` is the first release governed by this facade. `synaptic_tuner._version.__version__` is the canonical version source; `synaptic_tuner.__version__`, legacy `tuner.__version__`, distribution metadata, and CLI-reported version must derive from it and agree exactly.

### Plug-in signatures

Operational signatures stay compatible:

```python
class Renderer(Protocol):
    def __call__(self, row: Mapping[str, Any]) -> str: ...

class Grader(Protocol):
    def __call__(self, row: Mapping[str, Any]) -> Mapping[str, Any]: ...

class ContentEndResolver(Protocol):
    def __call__(
        self,
        full_ids: Sequence[int],
        prompt_len: int,
        tokenizer: Any,
    ) -> int: ...

class PluginFactory(Protocol):
    def __call__(self, context: PluginContext) -> object: ...
```

Discovery precedence:

1. host-manifest binding;
2. installed entry point in an authoritative versioned group `synaptic_tuner.plugins.<kind>.<vN>`;
3. legacy raw `module:callable` adapter.

Installed entry-point metadata contract:

- The entry-point group, not a caller-supplied request, is authoritative for both plug-in kind and public API major. For example, `synaptic_tuner.plugins.renderer.v1` declares renderer kind and v1 compatibility.
- Bulk discovery enumerates and validates the complete reserved `synaptic_tuner.plugins.*` namespace before applying a requested kind/API filter.
- Every reserved group must have exactly the `synaptic_tuner.plugins.<kind>.<vN>` shape and name a supported kind and API version. Malformed, unversioned, or unsupported reserved groups fail closed.
- Metadata discovery and all rejection paths operate without importing or loading plug-in code. Code is imported only through the existing explicit trusted-load boundary after metadata and the requested contract agree.
- Entry points outside the reserved `synaptic_tuner.plugins.*` namespace are unrelated and ignored.
- Manifest bindings retain first precedence, and the legacy raw adapter remains last; this metadata contract does not change either compatibility path.

Configs may use:

```yaml
execution:
  renderer: plugin://example.prompt
  grader: plugin://example.grade
```

Trust rules:

- A project plug-in is code execution authorized by the host project.
- It can read process memory, environment variables, credentials, and accessible files.
- Path containment protects engine-managed reads/writes; it does not sandbox plug-in code.
- Cloud launch must include plug-in identity/hash in the source lock.
- Imports are validated before GPU or paid submission.
- Duplicate bindings, malformed or unsupported reserved entry-point groups, and API-kind mismatches are fatal before plug-in import.

Event mode is newline-delimited `synaptic-event/v1`. Human output must never be mixed into machine-readable stdout. Diagnostics use stderr, and the final event contains or points to the result.

### Repository URL and credential contract

Source locks store only a sanitized canonical repository URL. They never store a credential-bearing clone URL.

```python
@dataclass(frozen=True)
class SecretRef:
    provider: Literal["env", "provider_secret", "credential_helper"]
    name: str

@dataclass(frozen=True)
class RepositoryLocation:
    canonical_url: str
    scheme: Literal["https", "ssh"]
    host: str
    path: str
    credential: SecretRef | None = None
```

Rules:

- Permit only policy-approved `https` and `ssh` repository transports for cloud reconstruction.
- Canonicalize SCP-like SSH notation to an internal `ssh://` representation before comparison and logging.
- Resolve a relative `.gitmodules` URL against the already approved canonical parent-repository URL, then apply the same scheme/host/path policy and store only the resolved sanitized identity.
- Reject HTTPS userinfo, passwords, access tokens, query strings, and fragments.
- SSH may use only an allowed non-secret transport username such as `git`; passwords and arbitrary userinfo are rejected.
- Strip default ports, normalize host case and path separators, and compare canonical host/path identities.
- Manifest policy declares allowed repository hosts, schemes, maximum nested-submodule depth, and whether nested submodules are permitted.
- Literal credential values are invalid in manifests, source locks, configs, events, and CLI JSON. Only `SecretRef` identifiers are accepted.
- Resolve credentials at execution time through the named environment/provider secret/credential helper. Never echo the resolved value.
- Private recursive submodules receive credentials scoped to the matching approved host and checkout duration. Do not place secrets in `.gitmodules`, clone URLs, command output, global Git config, or the source lock.
- Inspect and validate the committed `.gitmodules` document at every allowed recursion level before fetching that level. Reject disallowed schemes, hosts, paths, depth, URL rewrites, and unexpected nested submodules before network access.
- Disable local/file transports and unapproved Git protocol rewrites in cloud checkout.
- Remove temporary credential-helper and SSH configuration after checkout, including failure paths.

Negative tests must cover HTTPS tokens in userinfo, query credentials, fragments, SSH passwords, unapproved hosts, `file://`, protocol rewrite attempts, excessive nesting, an unexpected nested submodule, host-confused URLs, credential leakage in exceptions/events, and a private submodule whose `SecretRef` is absent or scoped to the wrong host.

### Canonical `superproject` mode

1. Validate that the host and engine worktrees are clean for cloud execution.
2. Read the engine gitlink from the host commit/index.
3. Require the checked-out engine `HEAD` to equal the gitlink.
4. Require both exact commits to be available from their declared remotes.
5. Clone the host at its exact commit.
6. Run `git submodule sync --recursive` and `git submodule update --init --recursive`.
7. Verify the checked-out engine path and commit against the source lock.
8. Validate the manifest, engine version, configs, plug-ins, and declared input hashes.
9. Create the runtime layout with source roots read-only and writable roots separate.
10. Begin provider/GPU work only after every check passes.

### Secondary `dual_clone` mode

- Clone host and engine separately at the locked commits.
- Place them into the same logical runtime layout used by superproject mode.
- Verify that the locked host gitlink still names the locked engine commit.
- Do not treat two arbitrary independently chosen commits as equivalent to a valid host dependency lock.
- Use only when recursive submodule checkout is unavailable or the engine is installed outside the host tree.

### Standalone mode

The project and engine source may be the same repository/commit. The source lock records `mode: standalone`; it does not invent a submodule relationship.

## Contract 8: Runtime Filesystem Layout

Logical layout shared by local Docker and cloud providers:

```text
/workspace/engine      read-only engine source/runtime assets
/workspace/project     read-only host source
/workspace/artifacts   read-write artifact root
/workspace/state       read-write resumable operational state
/workspace/tracking    read-write registries, source locks, resolved configs
/workspace/cache       read-write regenerable cache
/workspace/tmp         read-write recoverable staging
```

Host-side defaults:

```text
<project>/.synaptic/artifacts
<project>/.synaptic/state
<project>/.synaptic/tracking
<project>/.synaptic/cache
<project>/.synaptic/tmp
```

The checked-in host example includes a concrete default ignore policy:

```gitignore
# Synaptic Tuner runtime data; normal runs must not write into host source.
.synaptic/artifacts/
.synaptic/state/
.synaptic/tracking/
.synaptic/cache/
.synaptic/tmp/
```

An owner-approved export command may copy selected summaries to a separate checked-in host path, but normal execution does not weaken these ignores.

Local Docker bind mode mounts both source roots read-only. Copy mode copies engine/runtime assets to `/workspace/engine`, declared host inputs to `/workspace/project`, and returns outputs only from the writable roots. Normal execution never stages host data under engine `scratch/`.

Persistent container identity includes the engine commit, host manifest hash, runtime-layout schema, image identity, and dependency configuration. A container from one project context cannot be reused silently by another.

Read-only has two different enforcement levels:

1. **Container/cloud enforcement:** `/workspace/engine` and `/workspace/project` are mounted or materialized read-only at the operating-system/container boundary. Engine code and trusted plug-ins cannot write there unless they escape or possess broader host/provider authority.
2. **Native-process policy:** the path resolver and engine-managed writers reject source-root outputs, while a pre/post-run Git status plus tree snapshot detects accidental changes. This is policy and detection, not a sandbox. A trusted project plug-in runs with full process authority and can bypass engine-managed path APIs or write directly wherever the native process account permits.

Native no-write contract tests run representative built-in dry runs and CPU-safe operations, compare engine and host-source snapshots before/after, and assert that all engine-managed writes land below the declared `.synaptic` roots. Documentation and capability descriptors must not imply that native trusted plug-ins are contained. Projects needing containment for untrusted code must use a separate read-only container/process boundary; sandboxing is outside this plan.

## Security and Trust Model

### Assets and boundaries

| Asset | Trust/ownership | Required protection |
|---|---|---|
| Engine source | Trusted dependency, engine-owned | Read-only during host execution; exact commit |
| Host source/config | Trusted project input, host-owned | Read-only during runs; exact commit/hash for cloud |
| Project plug-ins | Trusted full-authority code | Explicit declaration, identity/hash, preflight import |
| Secrets | Operator/provider-owned | Environment/secret store only; never serialized |
| Artifacts/state/tracking/cache/tmp | Mutable host/provider data | Separate roots, containment, least necessary mounts |
| External paths | Operator-authorized local input | Cloud transport declaration and hash required |
| Source lock | Durable provenance | Atomic write, schema validation, remote verification |

### Threats and mitigations

| Threat | Mitigation |
|---|---|
| Path traversal or symlink escape | Resolve then enforce scheme-root containment; fail closed for writes |
| Dirtying the engine submodule | Read-only engine mount; contract test snapshots/git status; deny engine output targets |
| Host source mutation during execution | Host source mount read-only; writable roots separated |
| Host/engine provenance mismatch | Compare host gitlink, engine HEAD, source lock, and remote checkout before work |
| Unpushed commit produces unreconstructable run | Require both exact commits reachable remotely before paid cloud launch |
| Credential-bearing or host-confused Git URL | Canonicalize, sanitize, reject userinfo/query/fragment, enforce scheme/host/path policy |
| Private recursive submodule leaks a broad credential | `SecretRef` only, host-scoped ephemeral helper, pre-validate every `.gitmodules` level, remove helper on exit |
| Malicious nested submodule changes transport/host/depth | Allowed-host/scheme/depth policy and validation before each fetch |
| Config changes after signing/planning | Hash every source document and the resolved config; verify remotely |
| Plug-in substitution | Logical binding plus API kind and source/distribution hash in source lock |
| Secret leakage | Redaction policy; never include env values in plans, events, source locks, or resolved config |
| Command-stage shell injection | Preserve explicit `shell: true`; capability advertises arbitrary-command/full-authority effect and confirmation |
| Malicious plug-in | No sandbox claim; native engine-managed no-write policy cannot contain it; use a read-only container/process boundary if untrusted plug-ins are ever required |
| Cross-project persistent container reuse | Context-derived container identity and source-lock check |
| Provider bootstraps wrong source | Shared checkout verifier runs before dependency install/model download/GPU work where possible |
| Partial tracking/source-lock write | Atomic replace/locking; preserve prior complete record |
| Historical provenance corruption | No automatic rewriting/backfill of old records |

Security review gate:

- A security specialist reviews path containment, symlink behavior, source verification, command construction, redaction, archive extraction, and mount modes before provider launch.
- The review must explicitly state that trusted plug-ins are not sandboxed.

## Approved Owner Decisions

Joseph approved all six owner decisions on 2026-08-16. These are now implementation constraints rather than open questions.

1. **Initial public version:** Joseph confirmed on 2026-08-16 that the next Synaptic Tuner release is `1.1.0`. That release is the first distribution version declaring `synaptic_tuner.api.v1` and schema v1. `synaptic_tuner._version.__version__` is canonical; `synaptic_tuner.__version__`, legacy `tuner.__version__`, package metadata, and CLI reporting must derive from it and agree. The earlier instruction not to invent `1.0.0` is preserved as superseded rationale: `1.0.0` was rejected as an unconfirmed value for this refactor, not as a statement about historical repository identifiers.
2. **Legacy deprecation duration:** retain legacy compatibility for at least two minor releases and through one successful EHR migration. Legacy mode remains on the eventual removal roadmap; the compatibility window is a migration runway, not an indefinite support promise. Removal requires a separately reviewed breaking-release decision and migration evidence.
3. **Dual-clone delivery timing:** include dual-clone validation and schema support in the first release, then add provider execution after canonical superproject mode passes its gates.
4. **Checked-in derived outputs:** allow selected summaries to move from `.synaptic/artifacts` into source-controlled project directories only through an explicit `export` capability. Normal run output never writes into host source.
5. **Wheel runtime boundary:** defer public wheel publication until the runtime-asset inventory measures and resolves wheel size, editable-install behavior, shell-script needs, package resources, and container launch requirements.
6. **Tracking race scope:** fix the pre-existing `RunRegistry` concurrency race during the state-root phase in its own reviewable commit with a regression test.

The Wave 2 plug-in contract was clarified on 2026-08-16: installed plug-ins declare authoritative kind and API-major metadata through `synaptic_tuner.plugins.<kind>.<vN>`. Bulk discovery validates the complete reserved namespace before filtering; malformed, unversioned, and unsupported reserved groups fail closed without import, while unrelated groups are ignored. Manifest precedence and explicit trusted loading remain unchanged.

Every Create/Modify inventory row maps to exactly one implementation node and worker. Workers must not edit outside their rows or revert concurrent changes.

### Wave schedule with root plus three workers

This schedule uses strict merge barriers: no node in a wave starts until every node in the preceding wave has merged and root has rerun that wave's gate. Idle slots are intentional where a dependency cannot be safely parallelized.

| Wave | Root coordination/audit only | Worker 1 | Worker 2 | Worker 3 |
|---:|---|---|---|---|
| 0 | P0: approve plan, pin baseline, publish ownership ledger | — | — | — |
| 1 | Audit disjoint scopes and merge both | A project contracts | Idle; review only | C contract/security fixtures |
| 2 | Run foundation barrier; merge all three | D CLI/context | B public API/plugins | R runtime-asset boundary |
| 3 | Run CLI barrier; merge E | Idle; review only | E tracking/provenance | Idle; review only |
| 4 | Run standalone/embedded barrier; merge both | G domain adapters | Idle; review only | F local/discovery/batch |
| 5 | Run runtime-adapter barrier; merge both | I cloud foundation | Idle; review only | H capabilities |
| 6 | Run checkout/reconstruction/capability barrier; merge J | J HF Jobs | Idle; review only | Idle; review only |
| 7 | Run protected HF dry-run gate; merge both | Idle; review only | K Modal | L RunPod |
| 8 | Commission fresh QA; accept report or return defects to original node owner | Idle; no feature edits | M independent QA in an isolated worktree/assignment | Idle; no feature edits |
| 9 | Audit every release gate; merge N | Idle; review only | N docs/CI/release | Idle; review only |
| 10 | Authorize separate downstream work only after engine release acceptance | O separate EHR owner | — | — |

### Overlap rules

- Root does not edit implementation, tests, workflows, docs, or skills. Root maintains the ownership ledger, enforces barriers, audits diffs, and merges accepted commits.
- `tuner/project/source_bundle.py` is the only source-lock model. I/J/K/L consume it and may not introduce provider-local source dataclasses that duplicate it.
- A owns `tuner/project/__init__.py`, `tuner/project/manifest.py`, `tuner/project/context.py`, `tuner/project/path_refs.py`, `tuner/project/config_layers.py`, `tuner/project/errors.py`, `tuner/project/secrets.py`, and `tuner/project/source_bundle.py`. B owns only `tuner/project/plugins.py`. This is the only intentional split inside `tuner/project/**`, and their waves prevent concurrent edits.
- Provider boundaries are exclusive: I owns shared cloud foundation, J owns HF surfaces, K owns Modal surfaces, and L owns RunPod surfaces.
- QA owns only the two M paths. Feature tests remain with A–L/R/C, so QA never collides with implementation workers and never fixes what it audits.
- A failed M gate returns the defect to the original node owner in a new remediation wave. After that fix merges, a fresh QA specialist reruns M.
- N owns canonical skills and generated mirrors, but mirrors change only via the sync script. N also owns both workflow files.
- The downstream EHR owner never edits Synaptic Tuner; the engine workers never edit EHR in this plan.

### Merge gates

1. Wave 1 (`A`, `C`) must merge before Wave 2 (`D`, `B`, `R`).
2. `D` and `B` must merge before `E`; `E` must merge before Wave 4 (`F`, `G`).
3. `A`, `D`, `E`, and `R` are hard dependencies of the single-owner `I` node.
4. Wave 4 must merge before Wave 5 (`I`, `H`); `I`, `E`, and `G` plus `H` must merge before `J`.
5. Protected HF smoke must pass before `K` or `L` starts; both must merge before independent QA node `M`.
6. `M` must pass before `N`; no publication workflow or release is authorized before `N` passes.
7. `O` begins only after `N` and an accepted engine commit/release.
