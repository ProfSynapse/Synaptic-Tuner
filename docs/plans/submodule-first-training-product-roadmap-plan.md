# Implementation Plan: Submodule-First Training Product Roadmap

> Generated by `pact-codex-plan-mode` on 2026-08-26

## Summary

Synaptic Tuner has proven its core submodule-first hypothesis: an independent host project can pin the engine as a submodule, submit and recover a real Modal SFT run from exact source identities, verify its artifacts, and publish them to host-owned storage. The remaining journey is to remove Modal leakage from generic contracts, turn the proven vertical slice into one product API and CLI, bring local Docker, Hugging Face Jobs, and RunPod behind the same provider contract, expand methods and evaluation, delete legacy paths, and pass fresh-consumer release gates.

This is not a rewrite. The existing Modal lifecycle, evidence, source-lock, runtime-lock, verifier, and artifact-publication work are the reference implementation and regression corpus.

## Product Definition

A user supplies only:

- model and exact revision;
- dataset/reference;
- training method and hyperparameters;
- provider profile;
- artifact destination;
- approval when a paid effect is required.

The system owns:

```text
load → resolve → plan → preflight → authorize → start
                                      ↓
                     observe / logs / cancel / reconcile
                                      ↓
                              verify staging
                                      ↓
                       publish to host destination
```

Changing `docker` to `modal`, `hf_jobs`, or `runpod` must not change the workload or final-destination contract.

**Effort**: High


#### Mandatory boundary corrections

| Current leakage | Required correction |
|---|---|
| `HostPorts.modal_reads` | Generic host-owned provider session factory/registry |
| Modal defaults in generic provider contracts | Explicit, normalized provider descriptors and capabilities |
| Modal app/function/volume concepts in generic plans | Closed provider preparation documents behind a provider port |
| `modal_preparations` persistence | Provider-neutral prepared-operation records |
| Modal operations own generic lifecycle work | Extract one provider-neutral training coordinator |
| Host CLI hardcodes EHR, Modal, and submodule path | Project discovery plus manifest/plugin composition |
| Fixed five-file names in publisher | Verified manifest descriptors with host-selected publication naming policy |
| Public API re-exports implementation types | Public immutable contracts physically under `synaptic_tuner.api.v1` |

#### Public APIs

- `TrainingAPI`: load, resolve, plan, preflight, start, outcome, verify/reverify.
- `RunsAPI`: list, show, logs, cancel, reconcile, artifacts.
- `ArtifactsAPI`: destinations, publications, publish, verify publication.
- `EvaluationAPI`: explicit evaluation semantics sharing lifecycle machinery.
- `PipelinesAPI`: persisted train/evaluate/loss/analyze/publish DAGs and resume.

Do not collapse these semantic domains into an untyped universal job abstraction.

### Test And Security Phase

**Effort**: Very High

Highest-priority gaps:

- operational `cancel` and `reconcile` are not composed in the host;
- provider-call ambiguity after submission cannot always be reconciled;
- HF publication can duplicate commits after external success/local receipt failure;
- publication needs a durable state machine, destination readback, and crash recovery;
- local final verification still reads complete published files into memory even though transfer is streamed;
- project-local containment, symlink/junction/ancestor swaps, and directory durability need hostile testing;
- SQLite has no ordered migration framework;
- native Windows, recursive submodule CI, wheel install, and clean-consumer acceptance are unproven.

## Synthesized Implementation Roadmap

### Phase 0 — Freeze Evidence And Current Contracts

Purpose: preserve the working reference before refactoring it.

- Record the proven/implemented/unproven matrix in authoritative architecture docs.
- Preserve the exact successful Modal evidence, verifier false-negative, mount relocation, five-artifact inventory, and publication receipt as golden fixtures.
- Inventory every product/CLI path and classify it as canonical, migration-only, or obsolete.
- Define the public lifecycle/error/capability matrix.

Gate: the successful Modal run remains observable, verifiable, and publishable without another paid run.

### Phase 1 — Remove Modal From Generic Contracts

Purpose: avoid making HF Jobs and RunPod implement a Modal-shaped abstraction.

- Make public contracts import-light and independent of `tuner.*` and provider SDKs.
- Define explicit provider descriptors, capability declarations, staging identities, observations, logs, inventories, byte streams, cancellation, and reconciliation.
- Replace Modal-specific preparation storage with canonical opaque provider preparations.
- Extract generic lifecycle, grant, broker, verification, outcome, reverify, and publication coordination into one `TrainingCoordinator`.
- Introduce a lazy provider registry containing metadata and factories, never authenticated clients.

Gate: fake Docker, Modal, HF Jobs, and RunPod adapters can satisfy the same interfaces without provider fields entering public plans.

### Phase 2 — Build The Fail-Fast Conformance Ladder

Purpose: catch trainer and lifecycle failures locally before cloud spend.

- Create a deterministic fake-provider state-machine suite.
- Implement local Docker as the first real conformance provider.
- Use the same canonical workload, runtime assets, source identity, evidence, verifier, and artifact source as cloud providers.
- Add CPU/fixture CI, Docker Linux smoke, Docker Desktop copy-mode coverage, optional local GPU smoke, and forced interruption/recovery.
- Use immutable Docker labels for lookup/reconciliation rather than names alone.

Gate: the same SFT request can start, observe, cancel, reconcile, verify, and publish through Docker; source trees remain read-only.

### Phase 3 — Productize Modal Against The Generic Contract

Purpose: retain the proven mechanics while removing Modal-specific orchestration from the product boundary.

- Turn the current Modal stack into a thin execution-provider adapter.
- Keep its exact SDK/runtime locks, dual-source verification, Volume evidence, one-use effects, relocation logic, and redaction.
- Make the remote dispatcher method-blind but allow only engine-registered runtime assets.
- Compose list/show/logs/cancel/reconcile through `RunsAPI` according to declared capabilities.
- Prove the existing immutable successful run through the new coordinator.
- Run a new paid smoke only if the refactored remote path cannot be proven from existing evidence and all provider-free gates pass.

Gate: canonical API/CLI can plan, start, observe, reconcile, verify, and publish Modal runs without Modal concepts in the public request.

### Phase 4 — Consolidate Host Composition, State, And CLI

Purpose: turn the EHR reference integration into a reusable consumer pattern.

- Add host registries for providers, destinations, secrets, authorization, state, and workflows.
- Discover the host from `synaptic.yaml`; do not hardcode project ID, provider, submodule folder, or CWD.
- Make one product CLI call public APIs only.
- Introduce transactional ordered host-owned SQLite migrations.
- Implement provider-neutral prepared-operation, job-binding, verification, publication, and pipeline records.
- Preserve existing historical runs with a one-time migration or explicitly archive the development DB before the clean schema cut.

Target verbs:

```text
project validate
providers list/inspect/preflight/deploy
training validate/plan/preflight/start/status/logs/cancel/reconcile/verify/publish
artifacts destinations/publications/verify
pipeline plan/start/status/resume
```

Gate: adding a configured provider or destination requires no CLI dispatcher edit.

### Phase 5 — Make Publication A Durable Lifecycle

Purpose: make large local and remote publication crash-safe.

- Add `CLAIMED → TRANSFERRING → COMMITTED → VERIFIED`, plus `AMBIGUOUS` and `FAILED_BEFORE_EFFECT`.
- Claim before external mutation; bind deterministic destination identity.
- Stream writes and verification; never load a real checkpoint wholesale.
- Add directory/file durability, containment, link-safe access, disk-space preflight, orphan recovery, and concurrency tests.
- For HF, use compare-and-swap/parent commit protection, reconcile external success after local failure, and authenticate exact pinned-commit readback.
- Expose publication status, retry/reconcile rules, and verification.

Gate: kill/restart at every publication boundary converges without duplicate remote commits or conflicting local output.

### Phase 6 — Complete Hugging Face

Two independent proofs:

1. Live publish already-verified artifacts to a disposable user-selected HF repository; verify the exact commit OID and bytes without retraining.
2. Implement HF Jobs through the execution-provider contract.

- Reuse hardened exact-source, protected-approval, isolated Hub client, bucket-slot, anchor/sentinel, closed diagnostic, and artifact logic only where it conforms.
- Do not wrap the legacy `cloud-pipeline` as the new API.
- Prove preflight/control plane, smallest bounded SFT, fresh-process observation/reconciliation, exact artifacts, and host-selected publication.

Gate: the same canonical SFT request succeeds on Docker, Modal, and HF by changing provider configuration only.

### Phase 7 — Implement RunPod Cleanly

Purpose: add a third remote provider without changing generic contracts.

- Capture and digest the official REST/OpenAPI surface.
- Prefer Pods with Secure Cloud network volumes for long-running training unless research disproves that choice.
- Use provider secret references, exact image/runtime identity, source reconstruction, durable submission/cancel effects, network-volume evidence, and bounded S3-compatible readback.
- Model provisioning and execution as separate paid effects if the provider requires it.
- Run hermetic SDK/API tests, authenticated read-only preflight, control-plane smoke, cancellation smoke, and one bounded SFT smoke.

Gate: adding RunPod requires no public workload, lifecycle, or artifact schema change.

### Phase 8 — Expand Training Methods

Recommended order:

1. KTO
2. DPO
3. Embedding
4. GRPO
5. Environment-backed GRPO

Each method supplies a versioned config schema, deterministic compiler, whitelisted runtime asset, dataset validator, artifact contract, semantic verifier, Docker smoke, and provider-independent conformance tests. Provider adapters must not add method-specific orchestration branches.

Gate: every method passes locally before any paid-provider smoke.

### Phase 9 — Migrate Evaluation And Experiments

- Add public APIs for evaluation, exact loss, checkpoint selection, analysis, and pipelines.
- Persist stages separately and bind each stage to exact upstream artifact hashes rather than `latest`.
- Allow training and evaluation on different providers.
- Preserve partial success; evaluation or publication failure must not rewrite successful training as failed.
- Turn `run-experiment` into composition of public stage APIs rather than an HF-specific control plane.

Gate: Docker proves interrupted/resumed train → evaluate → exact loss → publish.

### Phase 10 — Delete Legacy Paths And Release

Because backward compatibility is not required, delete rather than forward once parity is proven:

- `cloud`, `cloud-run`, legacy training `cloud-pipeline`, protected-smoke product verbs;
- old backend registry entries and direct HF/RunPod orchestration;
- trainer-owned publication and ambient provider credentials;
- engine-owned scratch/state assumptions;
- duplicate host CLI and stale config trees;
- obsolete documentation, examples, and capability descriptors.

Keep `cloud-eval` until evaluation has its own migrated replacement. Replace removed-path tests with negative contracts preventing revival.

Recommended release boundary: package `2.0.0`, while keeping independently versioned public/config/persisted schemas at `v1` until their meanings truly change.

Gate: no production command imports the retired backend stack; wheel/sdist, recursive submodule, Linux, native Windows or explicitly supported WSL, and clean-consumer acceptance all pass.

## Cross-Cutting Decisions

| Decision | Recommendation | Rationale |
|---|---|---|
| First stable method | SFT only until provider parity | Prevent method/provider dimensions from multiplying together |
| Local Docker | First-class provider and conformance reference | Fast, cheap failure isolation and useful local product behavior |
| Publication behavior | Explicit core verb; workflow may auto-publish | Keeps training success separate from destination failure |
| Final destinations for first release | Local + HF | Port remains extensible without prematurely supporting every object store |
| RunPod product | Pods + Secure Cloud network volume, pending research | Fits long-running training and durable evidence better than endpoint inference |
| Legacy compatibility | None after new-path parity | User explicitly rejected compatibility shims and layered debt |
| Dirty local source | Only explicit content-addressed snapshot mode | Keeps reproducibility honest while supporting local iteration |
| Evaluation timing | Subsequent phase after training/provider foundation | Avoid deleting evaluation paths before replacement exists |
| Package version | `2.0.0` at hard legacy cut | Communicates intentional removal while schemas remain independently versioned |

## User Decisions Before Implementation

Recommendations are supplied so none must block initial Phase 0–2 work.

- [ ] **Existing SQLite history**: migrate current development runs into the generic schema, or archive the DB and start clean. Recommendation: migrate the proven Modal run so it remains an executable regression fixture.
- [ ] **Windows promise**: native Windows runtime or WSL-only. Recommendation: support native Windows for public/host contracts and Docker Desktop; allow provider launchers to remain Linux/WSL where SDK constraints require it.
- [ ] **RunPod release status**: required for first GA or preview. Recommendation: Docker + Modal + HF Jobs for first GA; RunPod remains preview until its live recovery/cancellation gates pass.
- [ ] **Cancellation requirement**: provider may ship without cancel or cancellation is mandatory for GA. Recommendation: require cancellation/reconciliation for every paid GA provider; capability-only unsupported status is acceptable for preview.
- [ ] **Provider staging retention**: automatic cleanup window versus manual retention. Recommendation: retain verified staging for a configurable recovery window; cleanup is a separate host-authorized action.

## Definition Of Done

The migration is complete when a fresh consumer repository can:

1. Add Synaptic Tuner at any submodule path.
2. Declare `synaptic.yaml`, model, data, method/hyperparameters, provider, and destination.
3. Run from any working directory without importing engine internals.
4. Keep engine and host source read-only during contained execution.
5. Keep every mutable file under host-selected roots.
6. Use one canonical API/CLI for Docker, Modal, HF Jobs, and any advertised RunPod support.
7. Resume, reconcile, cancel, verify, and publish safely across separate processes.
8. Produce exact source/config/runtime/workload/provider/artifact/publication lineage.
9. Pass the same SFT workload locally before paid execution.
10. Install from a clean wheel or consume as a submodule with all runtime assets present.
11. Pass supported Windows/Linux/Docker downstream conformance.
12. Contain no active legacy cloud-training backends or duplicate product verbs.
