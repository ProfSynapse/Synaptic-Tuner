# Config-first Modal training: implementation contract

Status: implementation decision for the approved [plan](../plans/config-first-modal-training-plan.md), 2026-09-22. This contract is limited to the first `python tuner.py train --job-config <recipe.yaml>` Qwen SFT path. The public `TrainingAPI` and the existing published-OCI route remain the launch boundary and compatibility baseline.

## Recipe and preparation (lane A)

Use the existing YAML mapping, not a second recipe schema. For this command, accept the existing `job.runtime_profile: qwen35-sft-v1`, `provider: modal`, `method: sft`, `model`, `dataset`, `training`, `lora`, and `artifacts` sections. The current recipe is a local Docker dry run: the Modal selection must explicitly change `provider` and `target`, set `run.dry_run: false`, and replace local-Docker-only `job` and artifact path settings. Reject unsupported keys rather than interpreting `job.image`, `job.image_qualification`, `run.trainer`, transfer/pull/container controls, arbitrary wheel or source paths, or executable commands as Modal authority. In particular, a `dry_run: true` recipe must never submit. Map the existing `training` and `lora` names to `TrainingInputV1`/`SFTTrainingHyperparametersV1` and `synaptic-packaged-sft-config/v1` with one explicit mapping function; check equality of canonical SFT controls, model revision, dataset identity, and artifact policy before planning. Preserve 32,768 context, Qwen revision `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`, preassigned splits, prompt-completion loss, and rank 32. Resolve the named profile from an allowlisted, checked-in profile map; the profile is not a user supplied image or release manifest.

The first `dataset.local_file` is a locator for the **published directory** containing `dataset.jsonl` and `manifest.json` (the path may name its `dataset.jsonl` member). Resolve it under an explicitly configured authorized prepared root. Use `verify_prepared_dataset_v2`/`snapshot_prepared_dataset_v2` from `tuner/dataset_prep/publication.py`, require its semantic identity, and retain its bytes/identity for staging. The first run's acceptance check compares the observed split counts with 181/39; the generic normalizer and host never hardcode those counts. A raw JSONL file or a mismatched manifest is refused. Add a registered `PublishedPreparedDatasetNormalizerV1` and its small path-free config to `tuner/training/input_preparation.py`; it implements the existing `TrainingInputNormalizerV1` protocol and returns the verified published directory already beneath the prepared root. This uses the current `TrainingInputPreparationServiceV1` requirement that the candidate's parent equal its attested root, and avoids republishing or changing the dataset digest. Then `TrainingInputPreparationServiceV1.prepare(LocalTrainingInputPathV1(...), TrainingPreparationConfigV1(...))` can reuse its independent format verifier and return `PreparedTrainingInputResultV1` with `prepared.identity`, canonical `prepared.request`, and `retained_source`. The host must retain that source through the one-use staging operation. The first live command runs on the existing supported WSL/Linux host with `PosixPrivatePreparedRootAuthorityV1`. Native Windows private-root support is deferred. Do not route a published pair through `DatasetPrepTrainingInputNormalizerV1`: that normalizer requires a source bundle and would change provenance.

Wire `CoordinatorTrainingService.prepare(source, config) -> PreparedTrainingInputResultV1` by injecting `TrainingInputPreparationServiceV1` through `build_training_operations` and `compose_family_coordinator`/`compose_reference_host`; keep the existing `TrainingAPI.prepare` signature. A consumer that omits the preparation port may still compose only if it gets a closed `preparation_unavailable` result on `prepare`; `load`/`resolve`/`plan` must remain compatible. The standalone Modal host supplies this port. Its read-only `--plan`/equivalent resolves and verifies the recipe and published input, compiles canonical workload, and prints profile, dataset digest/split counts, model revision, workload/config digests, runtime-material digest, resource request, and artifact policy. It must not call Modal build, deploy, stage, secret creation, or submit. Preparation may write only host-private input; if strict read-only planning is required, compute the same identity from a verified snapshot without publishing and assert equality at effectful preparation.

## Concrete standalone host composition (lane A, Modal only)

Make `train --job-config` construct the host graph internally, with `compose_reference_host(...)` as the central coordinator. It supplies `ReferenceHostPortsV1(records, streams, clock, grants, secrets)`, `ReferenceRequestPortsV1(loader, resolver, run_identity)`, `ReferenceAuthorityV1` from `compose_reference_authority(clock, secrets, authority_secret=SecretRef(...))`, and a Modal `ProviderFamilyV1`. `records` and `streams` use the public `DurableRecordStorePort` and `DurableStreamStorePort` semantics in `synaptic_tuner/api/v1/ports.py`; `compose_reference_stores` already turns them into planning, workflow, preparation, execution-grant and reconciliation-grant stores. `ReferenceAuthorizationV1` and `DurableEffectRepositoryV1` already compose grants and Foundation effects over the same record store. The CLI must supply concrete local implementations and configuration for these ports, not ask the operator to write callbacks. Credentials resolve from named host secrets; only references enter persisted canonical records.

The first command runs its coordinator in one process using `InMemoryDurableRecordStoreV1`/`InMemoryDurableStreamStoreV1`; it durably retains the one-shot submission claim, authenticated provider evidence, and retrieved artifacts in host-owned storage. `examples/modal_chat/storage.py` provides the private-path, one-shot attempt and catalog precedent, but its catalogs do **not** implement generic record/stream ports. An ambiguous effect consumes its claim and is never replayed automatically. This first command makes no claim that a fresh process can resume coordinator observation or reconciliation. A host-owned persistent implementation of the two generic store ports is a later, separately reviewed extension if restart recovery becomes required; no engine-owned lifecycle database is introduced.

Construct the Modal family from the existing `compose_modal_packaged_adapter(...)`: one explicit SDK 1.5.4 client, facade, deployment observer, input stager, reader, transport, effect/reconciliation resolvers, and host-owned binding/stage-receipt/call catalogs and one-use stage/dispatch sources. `ModalPackagedCatalogPorts`, `ModalPackagedSourcePorts`, and `ModalPackagedAuthorityPorts` are exact interfaces. The host must implement those protocols using its private storage and `retained_source`; it must not leave `resolve` callbacks unbound. The family planning and preparation collaborators must satisfy `describe/context/preflight` and `resolve/prepare/payload` in `ProviderFamilyV1`, with the existing packaged compilation and binding serving as their data source. Compose `TrainingAPI` from the returned training operations. The effectful order is `prepare -> load -> resolve -> plan -> preflight -> start`, followed by Runs/Artifacts observation and authenticated retrieval. Build/deploy preparation occurs before the provider execution binding is committed and before `start`, behind a separate explicit effect authorization and one-shot claim; it is never an incidental consequence of `plan`.

## Runtime material (lane B)

Add `synaptic-packaged-training-runtime-release/v2` as a closed tagged material union. Preserve `PackagedTrainingRuntimeReleaseV1` byte-for-byte parsing, its immutable `image.reference @sha256` rule, and published-OCI deployment. V2 shares the existing package, worker, Python, installed-distribution, platform, compatibility and contract facts, with a required `material` object:

| `material.kind` | Required commitment | Provider fact |
| --- | --- | --- |
| `published_oci` | final `image.reference` and matching `image.digest` | exact image/deployment facts as today |
| `modal_build` | pinned base OCI reference/digest; canonical build-input digest covering ordered commands, installer flags, current engine wheel, nine bootstrap wheel names/digests, builder policy and SDK version | actual Modal `image_id` plus app, generation, function IDs and deployment spec digest |

The build recipe is a provider-neutral ordered, declarative list of verified inputs and operations where practical; `modal_build` names the one implemented builder, and the provider-specific image ID lives only in Modal facts. Do not add a separate user-facing recipe schema. The release manifest digest is over the complete v2 document; never put the base digest in a field named final image digest or synthesize a final OCI digest. Existing generic `RuntimeSpec.image` requires final pinned OCI and `packaged_boundary.py` constructs it from `release.image_ref`; lane B must introduce a tagged material identity in that resolved-runtime path and its plan fingerprint, with a v1 branch retaining exact legacy behavior. Extend `ProviderRuntimeBindingV1`, `PackagedExecutionBindingV1`, packaged context parsing, and `ModalPackagedRuntimeFactsV1.validate_release` to accept the exact v1/v2 union without weakening cross-binding equality. The v2 Modal facts should commit `material_digest` and actual `image_id`, not a fictitious final image SHA. Version affected Modal deployment plan/facts only where their current `image_reference/image_digest` fields assume final OCI; old plans/facts remain readable and executable.

Source of build inputs: `Trainers/image_profiles/qwen35_4b_packaged_sft_3360351c/profile.yaml` pins base `docker.io/unsloth/unsloth@sha256:1644d635bc7c5b57ed64cabbab1ae00647dfb583c2135fdfb6a461aeeba52739`, `/opt/unsloth-venv/bin/python3` CPython 3.12.3, and the nine bootstrap wheels. Rebuild the engine wheel from the current accepted source and record its exact digest; do not reuse the old `3360351c` wheel hash after source changes. Reuse pure hash/staging/install/inventory checks from `tuner/cloud/derived_training_image.py`, without importing Docker receipt or publication assumptions. Image preparation uses Modal 1.5.4 `Image.from_registry(...).entrypoint([])`, copied verified files, bounded `run_commands`, and explicit `build(app)` as demonstrated by `scripts/capture_modal_inference_runtime.py`. Installation is `--no-index --no-deps --require-hashes` from copied wheels and occurs during image build, never in the training job. Compare `pip check` before/after; reject overlay-added conflicts while retaining the four recorded base conflicts. Capture installed distribution digest/count, Python/executable digest, package/worker closure and platform facts using the packaged runtime inspector. Model weights and prepared data stay outside the image.

After one authorized build, retain the returned Modal image ID. Deploy the two private training/self-check functions with that built image, not `Image.from_registry(base)`; read back the scoped app generation and exact function layout. Bind `release manifest digest + build-input digest + captured inventory + actual image ID + deployment spec/generation/function IDs` into authenticated Modal facts and the existing provider binding. Reuse a cached image/deployment only when all these facts and current scoped state still match. Modal current-state reads do not promise a version-pinned function lookup or readable function-to-image link; keep those limitations explicit and reject mismatches rather than treating a floating lookup as immutable proof. A build timeout, ambiguous deploy, changed source, new dependency conflict, image identity mismatch, or changed generation stops before job submission and consumes any one-use preparation/deploy claim as appropriate.

## Ownership and gates

Lane A owns recipe/CLI mapping (`tuner/handlers/train_handler.py` and CLI registration), input normalizer and `TrainingAPI.prepare` composition (`tuner/training/input_preparation.py`, `tuner/training/coordinator_service.py`, `synaptic_tuner/api/v1/reference/training.py`, `provider_family.py`, `composition.py`), and its host-only local port/catalog implementations. Lane B owns release schemas and runtime identity (`tuner/runtime/releases.py`, `tuner/training/contracts.py`, `tuner/training/packaged_boundary.py`), derived image preparation and Modal deployment/fact binding (`tuner/execution/providers/modal/runtime_release_deployment.py`, `packaged_binding.py`), plus corresponding schemas/locks/policy inventories. The only shared seam is the v2 release/material and provider-binding contract above; the orchestrator assigns any tests touching both lanes during integration. Neither lane edits the other's files without reassignment.

Verify in order: (1) pure recipe/prepared-v2/canonical-workload tests and plan with zero provider calls; (2) v1 release and developer-integration compatibility plus v2 malformed/identity/cache tests; (3) provider-free policy/lock barrier; (4) one authorized Modal image build and CPU self-check; (5) bounded GPU optimizer smoke with adapter save, five-artifact authenticated stream/rehash and reload; (6) full 181/39 run. The five roles and current 192 MiB/member, 256 MiB aggregate limits remain until measured output justifies a reviewed change. A CPU self-check does not qualify the optimizer, 32K fit, or adapter reload.

## First-run recovery boundary

The first path recovers the adapter by authenticating and retaining the completed artifact stream. It retains one-shot submission evidence even if the local process fails. The in-memory coordinator cannot resume observation or reconciliation in a new process, and the CLI must state that limit. No retry follows an uncertain submission. Persistent generic store ports and restart-time coordinator recovery remain future work.
