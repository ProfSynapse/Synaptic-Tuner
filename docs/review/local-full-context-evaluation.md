# Local full-context evaluation with vLLM

Status: draft workflow note with a bounded local-output checkpoint, 2026-10-02. Eight full-context local requests returned and the public/private response split was inspected; this is **not** a completed model-quality qualification. Do not infer determinism, semantic completion, or literary quality from a passing mechanical check.

## Reuse one pinned local server

Use the official vLLM OpenAI-compatible server with the reviewed, pinned base-model and tokenizer revisions, a verified local cache, and the intended LoRA adapter. Bind the served model/adapter name to the evaluation CLI's `--model` value and record the vLLM version, chat template, context limit, dtype, adapter identity, and launch settings. Start and qualify the server once; run controlled prompt variants against that same loaded model and adapter instead of reloading weights or submitting another training job. Check `/v1/models` and a small request before the long cases. Do not silently substitute a different revision or adapter to make a prompt fit.

Keep every selected source document, its order, and the full first-user-message text unchanged unless the named prompt variant explicitly changes the instruction. Profile the rendered prompt with the pinned tokenizer and check prompt-plus-generation room against the server's configured model context. If admission fails, record the exact failure; do not truncate documents, shorten the prompt, or drop a case while calling it the same evaluation. A local vLLM response may differ from an earlier hosted response because of server, template, scheduler, sampling, or runtime settings; retain the unmodified prompt as the baseline before attributing a difference to an instruction edit.

## Config-first request and bounded results

Put scenarios and inference settings in a private YAML config directory and run the existing `python -m Evaluator.cli --backend vllm --model <served-name> --config-dir <private-config-dir> --scenario <scenario.yaml> --host 127.0.0.1 --port <port> --output <private-results.json>` surface. Use `--dry-run` for scenario/config loading before making model calls. The `--timeout` and retry settings are request controls; retain their actual values with results. Use a new private output path per run.

`model.inference` at the top level of `eval_run.yaml` and the legacy nested `run.model.inference` form are both accepted. The nested inference mapping overrides matching top-level keys; explicit CLI inference flags take priority over both. This is a compatibility-sensitive change: top-level inference fields that older loading ignored are now honored. In particular, the checked-in example explicitly sets `temperature: 0.7`, `max_tokens: 2048`, and `seed: 42`; those are no longer equivalent to omitted fields. Where fields are absent, the CLI's legacy fallback is `temperature: null`, `max_tokens: 1024`, and `seed: null`. Compare the resolved inference metadata and wire request, not an assumed byte-identical legacy default.

An explicit YAML `max_tokens: null` omits the request-level output-token ceiling in the current vLLM client; omission of the YAML key instead falls back to the CLI default. Null does **not** remove the model context window, HTTP request/response and record-size policy, timeouts, GPU-memory limits, or any artifact limit. The separate same-job evaluation path has a reviewed 1 MiB HTTP request and response bound, 1 MiB retained-text bound, and 16 MiB signed evaluation-document bound; those values must not be projected onto the local `Evaluator.cli` client. Its generic HTTP client supports optional configured request/response byte bounds, while the ordinary vLLM factory path currently does not set them. Verify the actual local server/client and output-retention limits before long generation; do not interpret a historical 64 KiB same-job recorder discard as a local vLLM generation result.

## Thinking and trace separation

For thinking on/off comparisons, hold the model, documents, order, prompt variant, sampling settings, and server fixed. Set `chat_template_kwargs` in the YAML inference mapping, for example `enable_thinking: true` or `false`, and verify that the rendered request and model chat template support it. If the served model exposes a separate reasoning field, configure the vLLM reasoning parser appropriate to that pinned model and version at server startup, and verify its behavior from the actual response. The CLI's provider-specific `--reasoning-effort` flag is not a substitute for this vLLM chat-template toggle. Do not infer that thinking is off merely because public final text lacks a reasoning field.

The normal JSON/Markdown result is a public *projection* containing scenario questions, final response prose, scores, and errors; it must not merge raw provider bodies or conversation traces. A public projection is not automatically safe for external release when its scenario question contains private context. The optional `--private-trace-json <new-private-path>` captures raw fields in a separate create-only, host-local file for diagnostic comparison. It is opt-in and may contain sensitive prompt/context and reasoning text; keep it access-controlled and out of publication. Verify this separation in tests and retained responses on the intended platform. Judge final prose from the final-content field, not from reasoning text or a parser artifact.

## Compare, then conclude

Run the unchanged full-context baseline before edited prompts, then change only one instruction dimension at a time. Record the exact scenario identity, config digest, model/adapter identity, server flags, resolved inference settings, token counts, latency, finish reason, output bytes, and any local failure boundary. Review whether the final response is complete prose with a natural ending and whether it copies or paraphrases supplied outline instructions. Mechanical nonempty/natural-completion results are not author approval of style or narrative quality; a single stochastic sample per cell is exploratory.

`VLLM_BATCH_INVARIANT=1` is not universal reproducibility authority. In the local startup record, the engine rejected the mode with `RuntimeError: VLLM batch_invariant mode is not supported for GDN_ATTN.` Retain such an exact diagnostic and run only with a supported configuration; do not hide the failure or claim deterministic comparisons. vLLM's open [GDN attention batch-invariance issue](https://github.com/vllm-project/vllm/issues/48613) documents this for specific Qwen GDN architectures and version, not a rule for every model. Even with a fixed seed, a comparison must be reported as an observed local sample unless repeatability has been demonstrated under the exact serving configuration.

## Bounded local verification checkpoint

Eight local requests returned without request errors. In their retained records, each private trace's user message equals the corresponding complete scenario message; the unchanged baseline also equals its immutable dataset message by UTF-8 hash. The result's public final text equals the provider's final-content field. Four thinking-on responses have distinct reasoning fields in the opt-in private traces, absent from public case records. This verifies the observed client-side prompt and trace handling, not the server's internal attention to every document. Trace-file permission enforcement still needs its own platform check before treating storage as fully qualified.

Every retained response reported `finish_reason: stop` and passed only a configured nonempty (`length_min: 1`) scenario assertion, yet qualitative review found summaries, copied source structure, continuity mistakes, and in one unusually long case repeated source passages ending in an incomplete word. Thus `stop` is a transport/model stop reason, not semantic completion; neither it nor a technical PASS is author approval. Keep detailed prompts, raw reasoning, and story-specific comparisons in private experiment records rather than this checked-in note.
